## aot-relase-apk：重构成「拖 APK → 生成 GitHub Release」极简版

**背景**：用户要求从 0 到 1 做一个非常简单的东西 —— 只要拖 APK，就生成符合第三方抓取规范的 GitHub Release。
原先的工程有 5 个页签（上传/列表/邮件中心/GitHub 发布/监控），且 `services/releaseService.js` 语法错误导致服务根本起不来。

**用户明确拍板的 4 个决策**：
1. 推倒重写成极简版（删邮件/监控/本地版本库）
2. 版本号**自动解析 APK**（不靠文件名、不手填）
3. Token 放本地 `.env`（原本明文存在 `data/releases.json` 里）
4. 交付物**只有 GitHub Release 本身**（不要本地发版记录文件、不要额外发版脚本）

**发现的关键 bug（重要）**：
`services/githubReleaseService.js` 只剥离**小写** `v`（`replace(/^v/, '')`），tag 正则也写死小写 `/^v\d+\.\d+\.\d+/`。
而真包 `com.sunmi.sm3xr4ap.restaurant_desktop` 的 `versionName` 是 **`V2.14.5`（大写 V）**
→ 会算出 `tag = vV2.14.5` → 被自己的规范校验拦下。**就算服务没坏，这个真包也发不出去。**
修法：新增 `normalizeVersion()` / `toTag()`，统一 `/^[vV]/` 归一，tag 输出小写 `v2.14.5`。
已在 `test/test-github-release.js` 加「测试组 9」做回归。

**新增/重写的文件**：
- `services/apkInspector.js`（新）：`resolveAapt()` 按 ANDROID_HOME → ANDROID_SDK_ROOT → ~/Library/Android/sdk → ~/Android/Sdk
  的 `build-tools/*/` 取版本最高的 aapt2；`inspectApk()` 跑 `aapt2 dump badging`，
  用 `/(\w+)='([^']*)'/g` 抽 `package:` 行的全部键值对（不依赖字段顺序）；`md5File()` 分块算 MD5。
- `services/staging.js`（新）：`data/.stage/` 暂存，UUID 校验挡路径穿越，发布成功即清，1 小时残留自动扫掉。
- `server.js`（重写）：只剩静态服务 + `/api/config`、`/api/inspect`、`/api/publish`、`/api/latest`。
  `inspect` 用 `stream/promises.pipeline` 边落盘边算 MD5（60MB 不整包进内存）；**去掉了 CORS 头**（同源才安全）。
- `public/`（重写）：单页，拖拽 → 确认信息 → 正式版/测试版 → 必填更新说明 → 发布。
- `package.json`：`start` 改为 `node --env-file-if-exists=.env server.js`（Node 22 原生，无需 dotenv）。

**仓库卫生**：
- `data/releases.json` 与 `data/uploads/*.apk` 已 `git rm --cached` 并加进 `.gitignore`（`data/`、`*.apk`）。
- 核实过：那个明文 `ghp_` token **没有进过 git 历史**（只在工作区未提交的文件里），HEAD 是空串、origin/main 是 SSH 指纹串。
- 删掉：`services/releaseService.js`、`services/gitService.js`（SSH tag push 不再需要，建 Release 会自动建 tag）、
  `scripts/publish-release.js`、`sample-debug.apk`（391B 假文件）、test-engine/test-upload/test-server-api、mock-app-v1.apk。

**现状核实（用真实 GitHub API 查的，重要）**：
仓库 `ZJaCloud/aot-release-apk` 现在**已经存在**一个 Release `v2.14.5`（published、非 pre-release），
但 **`assets` 数量为 0** —— 所以第三方能读到版本号 2.14.5，却下载不到 APK，正是「查不到可用的安装包」的成因。
工具重发同一版本时会走 `422 already_exists` → `GET /releases/tags/{tag}` + `PATCH` → 补传 `.apk`，能直接修好。

**验证结果**：`npm test` 41/41（规范）+ 9/9（APK 解析）全过；
`curl POST /api/inspect` 传真实 60MB 包，正确得到 `com.sunmi.sm3xr4ap.restaurant_desktop` / `V2.14.5` / `v2.14.5`；
dry-run payload `tag_name: "v2.14.5"`、附件 `com.sunmi.sm3xr4ap.restaurant_desktop-v2.14.5.apk`。

**未完成 / 待用户操作**：`.env` 还没建、`GITHUB_TOKEN` 还没填 → **真实发布尚未执行**。
用户填好 token 后 `npm start`，拖入 APK 发布即可；随后可用页面上的「线上最新版自检」确认第三方能抓到 `.apk`。

对 `ZJaCloud/aot-release-apk` 的 `permissions.push = true`）。
。
所以之前以为「`data/releases.json` 里明文存了真 token」其实是**那个占位串**——真值从未落进那个文件。
（但仍按泄漏预案处理：文件已删、`data/` 与 `.env` 都已 gitignore。）

**新增配置**：`.env` 里加了 `GITHUB_APP_NAME`，server.js 用它覆盖默认应用名。
设为 `TPOS 客户端`（沿用 GitHub 上已有 Release 的显示名，而不是代码里的默认值 `TPOS 餐厅收银桌面端`）。

**发布结果**（`POST /api/publish`，耗时 16 秒）：
- 走的是「Release 已存在」分支：POST → 422 `already_exists` → `GET /releases/tags/v2.14.5` → `PATCH` → 上传附件
- Release id `414387055`；asset id `645670634`，`com.sunmi.sm3xr4ap.restaurant_desktop-v2.14.5.apk`，63,520,521 bytes
- 更新说明沿用原有的「日常构建更新，性能优化与稳定性提升」，没有自己编内容

**独立验证（全部通过）**：
- `GET /releases/latest` → `tag_name = v2.14.5`，`assets` 数量 **1**（之前是 0），`state=uploaded`
- 附件下载 URL → HTTP 200，`Content-Type: application/vnd.android.package-archive`
- **把 60MB 附件下载回来比对 MD5：线上/本地都是 `0721ea07c100dca907fd744030f14ab0`**，字节完全一致
- 发布成功后暂存文件已自动清理；另手动清掉了演练残留的 61MB

**结论**：第三方「查不到可用的安装包」的问题已解决。仓库同时只能有一个 Latest，后续发新正式版会自动把 v2.14.5 降级。
